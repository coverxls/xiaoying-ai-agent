# 05 · 复盘

## 1. 最难的问题

### 1.1 “建议 19:00”不等于“改成 19:00”

一开始很容易把冲突处理写成：发现 18:00 被占用 → 查 19:00 → 保存 19:00 草稿 → `completed`。这看起来完成了任务，但违反了题目的核心边界：用户要求 18:00 是硬性的，未经同意不能改。

最后的处理是：

- 保留 `requested_time=18:00`；
- 草稿 `slot=19:00`，`draft_status=pending_confirmation`；
- 输出 `status=pending_confirmation`、`changed_from_request=true`、`pending_items` 明确要求确认；
- finish 校验禁止把“改了时段的草稿”标成 `completed`。

这个边界比“能跑通”更重要，也是本题最能区分普通串行调用和真正 Agent 的地方。

### 1.2 幂等不是“再查一次”

最直接的防重复是“保存前查一下有没有”。但在并发下这是 race。这里用存储层幂等键：

```text
sha256(material_id|date|slot|requested_time|draft_status)
```

相同键直接返回已有 `draft_id` 和 `duplicate=true`。测试覆盖了正常草稿重复，也覆盖了“冲突后 19:00 待确认草稿重复”，避免只验证一种情况。

### 1.3 保存失败不能“看起来成功”

初始实现里，工具失败后模型可能仍然输出“已保存”。最后的做法是：

- 工具返回 `ok=false` 和明确 `error`；
- finish 校验要求 `save_failed`；
- 输出 `draft.ok=false`、没有 `draft_id`；
- 测试断言 message 含“失败”，不含“成功”。

真实运行中模型还重试了一次，第二次仍失败才结束；这比“一次失败就放弃”更接近实际，同时没有伪造成功。

### 1.4 模型参数错误是常态

真实运行出现过 `slot="10:00-10:01"`，工具返回 `invalid_arguments`，模型改成 `10:00` 后成功。这个失败被保留在 `examples/05_duplicate/first_run_trace.md`，因为它恰好证明：

- 工具没有静默容错；
- 模型看到了错误；
- 下一步动作发生了变化。

如果把它藏掉，只展示一条完美路径，反而失去“ReAct 决策”的证据。

## 2. 学到什么

1. **Agent 的难点不在“调工具”，而在状态与边界。** 工具调用本身很简单；难的是保证“什么时候不能继续”“什么结果不能宣称成功”。
2. **Trace 是产品的一部分。** 只记录最终 JSON 不够，评审需要看到每一步的参数、observation 和下一步依据。
3. **Mock 是测试夹具，不是效果证明。** Mock 能稳定测状态机；真实模型才能暴露参数格式、措辞和重试行为。
4. **校验层要“拒绝并解释”，不要直接抛异常。** 把拒绝原因作为 observation 还给模型，既保留 ReAct 循环，又能让模型自我修正。
5. **批量不是循环调用单次接口。** 如果不在工具层记录“本批次已占用的草稿”，第二个素材会查到同一个空档，产生两份同时段草稿；批次内占位是批量排期的最小正确性条件。
6. **3 小时约束下，少即是多。** 不做 UI、多 Agent、真实发布，把时间花在冲突、确认、幂等、失败四条线上。

## 3. 如果重做，会怎么改

- 用 JSON Schema 校验模型动作，减少 `slot` 格式错误；
- 把草稿存储换成 SQLite/Postgres，加唯一索引和事务；
- 批量已支持，但批次内占位不跨批次；下一步做优先级、截止时间排序和跨批次占位；
- 增加“用户确认”入口：只有确认后才能把 `pending_confirmation` 转为 `scheduled`；
- 增加审核缓冲、跨平台冲突、节假日；
- 给模型动作加成本/延迟统计，比较不同模型的决策质量；
- 增加更真实的“工具超时/部分成功”场景。

## 4. 时间记录

- 题目确认后，核心实现、测试、9 组真实模型运行与 examples 整理约 45–55 分钟（AI 辅助，2026-10-28 12:04–13:05 左右）；
- 前期需求澄清、环境检查、凭据确认另计；
- 候选人最终复核、建仓/push、填写 URL/SHA 的时间未计入。

## 5. 未完成部分

以下不是题目必需，但在生产化前需要补：

- 批量优先级/截止时间排序与跨平台冲突；
- 真实发布平台对接（本题明确不接）；
- 数据库持久化与并发控制；
- 用户确认 UI/API；
- 多模型对比与成本控制；
- 更细的审核缓冲与时段约束。

## 6. 一句话总结

这个项目最重要的不是“让模型跑完四个工具”，而是让它在**该停的时候停、该问的时候问、该失败的时候承认失败**。冲突换时段、待确认草稿、幂等保存和保存失败，是这次实现真正花时间的地方。
